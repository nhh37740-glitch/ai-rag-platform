      我如何解释这个项目 架构、取舍与原型边界
      

        
一条可以讲清楚的请求链路

        
HTTP 接口接收固定问题 → Agent 加载检索指令并调用 LLM → ToolRegistry 执行只读 RAG 工具 → rag-core 在内置知识库中检索 → 工具返回片段 → LLM 输出回答。RequestContext 的 trace_id 把各模块执行串起来。

        
为什么保留模块化与 Jenkins

        
共享契约规定模块接口，各模块独立实现与版本管理。服务器 Jenkins 负责测试、Linux 二进制编译、契约与运行来源校验，门禁通过后才能交付；运行进程只加载发布工件。页面上的 trace 展示请求执行，不代表 Jenkins 构建证明。

        
这次演示能证明什么

        
可以核对一次固定问题的回答、实际检索来源和调用记录。模型与 embedding 标签来自服务器配置：DeepSeek 是真实模型调用；Mock 是离线工具流程演示；hash 是离线向量方案，不能当作 BGE 语义检索质量。

        
还没有完成什么

        
这是固定问题、内置公开资料、只读工具的原型。知识库 scope 过滤不是用户鉴权；尚无生产级准确率或可信度评测。检索分数不是答案置信度，不能跨检索方式直接比较。当前 Web 未接入 MCP，也未依赖 LangChain、LangGraph 或 Hermes；Skill 是指令加载，不是可持久恢复的工作流。

        
各 span 有嵌套关系，耗时单独显示，不相加。缓存命中会复用原请求的答案与 trace，因此缓存记录里的耗时不是本次重新推理耗时。
